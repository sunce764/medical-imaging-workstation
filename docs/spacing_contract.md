# 一个未被满足的推理契约

**如何发现产品违背了模型的前提假设，量化它的代价，修好它，再说清剩下什么没测。**

---

## 症状：一个测不出来的错误

这个 CT 工作站内置一个 ONNX 分割模型，输出 24 个腹部与胸部器官。它随附时没有任何说明其来源的元数据——没有 `dataset.json`，没有训练配置，标签映射也是空白。

早先的工作用一例带真值的公开 CT 把它的身份**实测**了出来：跑推理、与真值算标签重叠混淆矩阵、得到干净的对角线，实测出它的标签方案就是 **TotalSegmentator v2 `class_map_part_organs`**，一个 nnU-Net v2 导出。（被实测的是标签映射本身；「这份权重即该上游 release」是由此得出的强推断，不是密码学证明。）同一次实验给出 21 个在场器官的平均 **Dice ≈ 0.92**。

这个数字在项目里挂了很久，看上去无可指摘。

问题出在它是**怎么**测出来的。

用于验证的那例数据是 **1.5 mm 各向同性**。而 nnU-Net 的推理契约规定，第一步必须把体积重采样到训练时的 spacing——对这个模型，正是 1.5 mm 各向同性。

也就是说：**验证恰好发生在失配为零的那个点上。**

而产品的推理引擎从不做这一步：

```
$ grep -n "resample\|zoom\|spacing" ai_engine.py
（无输出）
```

ONNX 图里也没有 `Resize` 算子——重采样不在模型内部。产品把每个序列按其原始 spacing 直接送进网络。

随附的另一套数据是 0.712891 mm in-plane、1.25 mm 层厚。**它从未被测量过。**

这类缺陷最麻烦的地方在于：它不会崩溃、不会报错、不会在任何测试里失败。分割照常产出，颜色照常叠加，定量照常显示。唯一的异常是准确度——而准确度恰恰是没人去量的那个量。

> 不是"可能略低一些"。是**未测量**。这两者的区别，就是这篇文章的全部。

---

## 第一步：量化代价

要知道跳过这一步值多少钱，只需要一个受控实验。

取那例 1.5 mm 的带真值数据，重采样到若干偏离的 spacing，跑同一套推理，再把预测**最近邻映射回原网格**，与**未经改动的真值**算 Dice。真值全程不参与插值——因此 Dice 的任何下降都只能归因于 spacing 失配本身。

| 送入模型的 spacing | 1.5 mm（训练值） | 1.75 mm | 2.0 mm | 2.5 mm | 3.0 mm |
|---|---|---|---|---|---|
| 21 器官平均 Dice | **0.9219** | 0.8998 | 0.8813 | 0.8288 | **0.7995** |
| 相对基线 | — | −2.4% | −4.4% | −10.1% | **−13.3%** |

spacing 翻倍，掉 13%。

> 该消融与上表全部跑在模型自身的 RAS 面内方位上，两臂都不经产品的
> DICOM（LPS）路径——因此它量的是 spacing 这一个变量对**模型**的影响，
> 不是产品端到端的表现。

**但均值是这里最不重要的数字。**

拆开看逐个器官，失效的形态完全不同：

```
gallbladder   0.82 → 0.89 → 0.45 → 0.10 → 0.55     ← 非单调，一度近乎完全失败
adrenal_L     0.92 → 0.83 → 0.83 → 0.71 → 0.58
thyroid       0.79 → 0.69 → 0.81 → 0.76 → 0.56
liver / kidney / lung lobes                        ← 全程 > 0.85
```

小结构最先垮，而且**不是单调下降**——胆囊在 2.5 mm 处跌到 0.10，几乎整个器官分错，到 3.0 mm 又回升到 0.55。大器官几乎不受影响。

于是出现了这样一种局面：总体 Dice 还写着 0.80，看上去"可用"，而其中某几个器官已经实质失效。**一个聚合指标最不擅长暴露的，恰恰是这种个别塌陷。**

一个附带发现：这条曲线还解释了为什么问题此前不可见。所有历史证据都取自曲线最左端那一个点，而那个点是全曲线的最大值。

---

## 第二步：修复

修复本身不复杂——推理前重采样到 1.5 mm，推理后把标签图与置信度**最近邻**映射回原网格。真正需要判断的是三处边界条件：

**不知道 spacing 时不做。** 插值必须基于真实物理尺寸，猜一个只会更糟。

**已经足够接近时不做。** 各轴都在 5% 以内就跳过——重采样自带插值损失，为消除 5% 的失配而引入一次插值不划算。

**放大后会超内存时不做。** 对**粗** spacing 重采样是放大，5 mm 层厚的序列 z 方向可涨 3 倍以上。此时宁可维持失配，也不能把应用跑崩——但必须打印出来，让人知道这次跳过了。

还有一处**不该照搬 DICOM 标签**的地方：层间距不能取 `SliceThickness`。那是探测器准直厚度，而重采样需要的是层与层的实际间隔；重叠重建下二者可差一倍。改为由相邻层的 `ImagePositionPatient` 实测。**当时保留了 `SpacingBetweenSlices` / `SliceThickness` 两级回退，现已取消**：`dicom_geometry.analyze_series` 要求投影位置本身有限、唯一且等距，否则该序列判为几何不可用（fail closed），不再用标签值补一个可能错一倍的间距。本节记述的是引入实测间距那一次改动，回退分支属其后被移除的历史实现。

> 随附数据恰好两者都是 1.25 mm。**这个错误在本机永远暴露不了**——顺着查下去发现器官体积、三维网格 z 尺度、MPR 冠矢状面宽高比全都继承了同一个错误，一并统一。

---

## 第三步：验证——单例会骗人，而且方向不可知

修完之后，最容易犯的错是拿一例数据一跑，看到提升就收工。

在同一例 s0029 上，修复带来 **+0.064**。

但这个项目此前已经栽过一次：肺叶 Dice 在单例上是 0.956–0.991，扩到 57 例后变成 **0.887**——单例偏乐观。有了这个教训，就该问：这次的 +0.064 靠得住吗？

于是做了 **20 例配对验证**：同一份失配输入，一条走直通（修复前行为），一条走产品引擎（含重采样）。在同一条 RAS 输入路径上，两者唯一的差别就是这一步，因此差值的分布直接就是这一步的效果分布（两臂都不经产品的 DICOM/LPS 方位，故这是模型侧的效果，不是产品显示结果的效果）。

| | 直通 | 经引擎 |
|---|---|---|
| 20 例平均 Dice | 0.684 | **0.840** |

配对差值 **+0.1554**，95% CI [+0.110, +0.211]，Wilcoxon signed-rank **p = 1.9×10⁻⁶**，**20 例全部改善**。

**当初挑中的那一例 s0029，改善幅度落在整个范围的低端。** 单例把真实效果低估了 2.4 倍（+0.064 对 20 例均值 +0.155）。注意 s0029 本身不在那 20 例之内；若并入排名，它是 21 例里的倒数第三，而非最小。

于是同一个项目里出现了两个方向相反的单例失真：

| | 单例 | 多例 | 方向 |
|---|---|---|---|
| 肺叶 Dice | 0.956–0.991 | 0.887（57 例） | 偏**乐观** |
| spacing 修复 | +0.064 | +0.155（20 例） | 偏**保守** |

结论不是"单例总是偏乐观"。是**单例的偏向事先不可知**——这一条现在写在项目的技术报告里。

均值同样掩盖了最有说服力的部分。最极端的一例：

```
s0221:  0.0986  →  0.6552
```

不做重采样时，那一例**整体失败**，不是"稍差"。

## 顺带的收益，与真实的代价

修复之后，随附序列的推理开销：

| | 修复前 | 修复后 |
|---|---|---|
| 体素数 | 61.1 M | 11.5 M |
| 耗时 | 100 s | **37 s** |
| 峰值内存 | 8.8 GB | **3.0 GB** |

对细 spacing 数据，重采样是**降采样**——准确度与开销同向变化，不需要权衡。还有一个不明显的好处：重采样到固定 1.5 mm 之后，体素数只由扫描 FOV 决定（胸腹 CT 恒在 19 M 上下），推理的耗时与内存**不再随扫描协议波动**。

但它不是纯赚。

蒙版边界现在是在 1.5 mm 网格上决定的，映射回更细的原分辨率后呈阶梯状——0.713 mm 数据上实测约 2 像素平台。这个误差会继续传导到三维形状特征：以解析球实测（[`mesh_spacing_effect.py`](../experiments/mesh_spacing_effect.py)），表面积偏差从 +0.26% 变为 **+1.95%**，体积偏差 −0.18% → **−0.97%**，球形度 0.9962 → 0.9745。

**结构级准确度上升，像素级边界精度下降。** 拿形状特征做定量比较的人应该知道这一项。

## 还剩什么没测

**更细 spacing 的一侧没有实测。** 32 GB 机器只测得到变粗方向；把 1.5 mm 的例子上采样到 0.71 mm 会使体素数增至 9.4 倍（约 3.6 亿），推理峰值需 50 GB 以上。随附数据恰好落在这一侧。现在的说法是"该侧属降采样、信息本就充足，原理上比已测的变粗侧更有利"——**这是推断，不是测量**，模型说明卡里就这么写。

**扫描范围过大时仍会跳过重采样**，此时失配依旧存在。

**样本仍然小且来源单一。** 20 例全部来自同一个公开数据集，其他扫描协议与设备未测。

---

## 这件事教给我的

**一个恰好通过的验证，比一个失败的验证更危险。** 0.92 是真的，实验方法也没问题——问题在于它只覆盖了 spacing 失配为零的那一个点，而这一点从没被写下来过。缺陷不在数字里，在它的适用范围里。

**均值是最不擅长暴露个别塌陷的统计量。** 0.80 的总体 Dice 背后，可以藏着一个跌到 0.10 的器官。这也是产品界面现在逐器官报告置信度、而不只报一个总数的原因。

**先量化，再动手。** 13% 这个数字是后来所有决定的依据——包括判断它值不值得修、修完怎么验证、以及哪些边界必须说清楚。没有它，这就只是一次"按文档改对"的改动，说服不了任何人。

**如实声明没测的部分，不比测出来的部分次要。** 细 spacing 侧、大范围扫描的跳过、边界精度的代价——这三条都写在产品界面的模型说明卡上，卡上的每个数字都从实验产物现读，重跑实验会自动更新。

## 复现

前置：`s0029` 必须已在 `experiments/.seg3d_cache/`（`seg_spacing.py` 只从该目录读取），
获取方式见 [`experiments/README.md`](../experiments/README.md) 的 Study II 一节。

```bash
python experiments/seg_spacing.py 1.75 2.0 2.5 3.0   # 消融曲线
python experiments/seg_spacing.py engine 3.0         # 单例：直通 vs 产品引擎
python experiments/seg_spacing.py multi 3.0 20       # 20 例配对验证
```

数据为 TotalSegmentator-CT-Lite（CC-BY-4.0）公开去标识研究数据，manifest 记录固定 revision。`engine` / `multi` 两臂运行时直接调用产品的 `ai_engine`；默认消融臂走的是 `seg_validate.run_onnx`——对 `ai_engine` 推理循环的复刻，且停在末窗回移（`2a50e37`）之前，不是产品代码本身。两臂不在同一末窗写法上，且都以模型的 RAS 面内约定喂入，而非产品 DICOM 的 LPS。
